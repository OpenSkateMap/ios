# ContributionsKit

**Purpose:** Gets new spots from the person to the curators: the outbox that sends them and their photos (and keeps them across relaunches and dead networks), and the history of what curators decided.
**Tier:** Services
**Project deps:** `APIClientKit`, `SQLiteKit`, `SpotModelKit`, `PhotoUploadKit` (the spots' photos) (packages: `FactoryKit`, OpenAPIRuntime, `SQLiteData`)
**Public Factory keys:** `contributionsSession` (`@MainActor`, `.scope(.account)`), `contributionsOutbox` (`.singleton`), `contributionsAPIManager`, `videoLinkChecker` (`.singleton`, `.onPreview`), `backgroundTime` (`.none` until the app binds it)
**Entry points:**
- `ContributionsSession` — `@MainActor @Observable` facade: `prepare(_:)` (a picked photo → PhotoUploadKit's `PreparedPhoto`), `submit(_:)`, `retry(_:)`, `discard(_:)` (false when the entry is already uploading: it isn't taken back), `refresh()`, `pull()` (the same refresh for a person's pull, saying whether the history came back), `nearbySpots(latitude:longitude:)`.
- `ContributionsOutbox` — actor and the only writer of `submission_draft`, `draft_photo` and `my_submission`. New spots (`add(_: NewSpot)`) and suggested edits (`add(_: SpotEditSuggestion)`: the proposed fields, `changedDetails`, and `photoEdit`, the spot's whole photo list as the edit leaves it: `order` of `.kept(id:)` and `.added(photo)`, the cover first, and `base`, the list the editor showed; nil leaves the photos alone, and `changedFields` adds `.photos` only when it's set) share the row and the pipeline; an edit's row has `editsSpotID`, and `save` sends it to `PUT /v1/spot-edits/{id}` with only the changed fields. The outbox walks an edit's `order` once, writing each added photo and building the list of ids into `photoOrder` and `basePhotoIDs` (the columns stay; set together), which go out as `photoEdit`; an edit's new photos are only its slots' (`proposed.photos` stays empty). Serial passes (`kick()`); photos first, then `PUT /v1/submissions/{id}` with the same ids on every retry; a sent entry moves to the history in one transaction; `missingPhotos` re-uploads once per pass; transient failures back off (1 s doubling to 60 s, jitter 0.5–1) with a scheduled wakeup; permanent refusals mark the entry `failed` with the server's reason. `reset()` stops it and clears everything for an ended account.
- `ContributionsAPIManager` — `save`, `mySubmissions`, `nearby`, `saveVideo`; failures as `ContributionsAPIError`. Calls go through APIClientKit's `SessionCredentials.authorized` (`APICall.swift` passes this module's errors and maps a photo upload's `PhotoUploadError` into them, so the outbox handles both alike).
- `VideoLinkChecker` (`videoLinkChecker`, `.singleton`, `.onPreview` never asks) — whether a parsed `VideoLink` plays: YouTube's keyless oEmbed (`.available(title:author:)`, `.unavailable` for 400/401/403/404, `.unknown` for anything else, Instagram included). Add Video asks before Send; the server asks again for a new video.
- `NewSpot` — what the submit flow hands over (`PhotoCredit` and `NearbySpot` live in SpotModelKit, shared with ReviewKit).
- `OutboxFiles` — prepared JPEGs in `Application Support/Outbox`, excluded from backups. Files no row names (a crash between writing a photo and its row, or a database `AppDatabase.openOrRecover` recreated) are removed by the first pass of each process, once older than ten minutes.

- **Private spots:** `NewSpot.collectionID` (one of the account's private collections) goes out as `collectionId` on the submission. The server publishes it at once, unreviewed, into that collection. Once one is sent, the outbox runs `PublishedSpotHandler` (Factory key `publishedSpotHandler`) with `.private`, which the app answers with a collections pull, because private spots don't come with the spot sync.
- **Published at once:** the outbox runs the same `PublishedSpotHandler` for any entry the server answers as approved (an admin's spot or edit), with `.public` (a spot sync) unless it went into a collection, so the map shows it without waiting for the next foreground (Ertem, 2026-10-30).

**Ownership map:**
- Unsent spots, their photos and their send state → `ContributionsOutbox` (rows) and `OutboxFiles` (bytes).
- What curators decided → `my_submission`, brought to the server's list by `ContributionsOutbox.refreshHistory()`: rows known before the request that the server no longer lists go, and only the rows that differ are upserted (an unchanged history wakes nothing), so an entry sent while the request was out stays. `ContributionsSession.refresh()` and `pull()` join a refresh already running.

## Rules

- Never write the contribution tables outside `ContributionsOutbox`. Every write in a pass is checked against `generation`, so nothing from an ended account is written back.
- An entry's id and its photos' ids are minted once, when it enters the outbox, and never change: that's what makes retries idempotent on the server.
- `uploading` is never left behind: the first pass of each process (and the first after `reset()`) turns it back into `pending` before it sends anything, so nothing it touches is being sent (a pass cancelled before that finishes leaves it to the next pass). A cancelled send writes `pending` back from a task of its own, since a cancelled task's database writes throw. `start()` only kicks a pass.
- Every pass runs inside `BackgroundTime` (Factory key `backgroundTime`; the app binds it, so this module doesn't import UIKit or BackgroundTasks): a submit made just before leaving the app still goes out, and when the time runs out the pass is cancelled and its entry waits as `pending`.
- **A pass someone starts by sending photos is shown** (`run(shownAs:)`, Ertem 2026-10-20): adding a spot or an edit with photos, or retrying one with photos still to upload, runs that pass with `BackgroundProgress`. Each photo is a step, then each entry's save, recounted before every entry, and the line under the title says which photo is going ("Uploading Spot", "Photo 2 of 5"; `outbox.upload.*`). The app turns it into a continued-processing task (iOS 26 `BGContinuedProcessingTask`): the system shows it as a Live Activity and keeps the upload going after the person leaves the app, past the usual ~30 s. Cancelling it there is the same as the time running out: nothing is lost, the entry waits as `pending` for the next foreground. Launch, foreground, wakeup and video passes, and entries without photos, keep plain background time. A person's add while another pass runs joins that pass as it is.
- `problem` is set only on a `failed` entry (the server's reason, or why this device can't send it); a backoff shows through `attempts` and `nextAttemptAt`.
- The duplicate check (`nearby`) is a hint, never a gate: it answers empty when it can't tell.
- Tests use `FakeContributionsServer` (the M4 contract in memory; `sentEdits` keeps each edit as it goes on the wire), a temporary `OutboxFiles` folder, a hand-moved clock for `now`, and drive passes with `drain()`; no sleeps.
